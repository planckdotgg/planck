# Bidirectional audio and clipboard (Phase 1)

Research: `planck-design/audio-clipboard-research.md` §3–§9.

## Host → client desktop audio

- Windows: WASAPI process loopback (`ActivateAudioInterfaceAsync` on
  `VAD\Process_Loopback`, `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`,
  target = Planck's PID). Falls back to default-endpoint loopback when
  activation fails (builds before 20348). The API takes one target tree, so
  extra excluded PIDs are not possible in one stream; `CaptureOptions.ExcludePIDs`
  is honoured on macOS and reported as unsupported on Windows.
- macOS: Core Audio process tap (`CATapDescription` global stereo tap that
  excludes Planck's process object and `ExcludePIDs`) on a private aggregate
  device, read with a HAL IOProc. Falls back to ScreenCaptureKit below 14.2,
  on any error, or when the tap is not 48 kHz.

## Client → host microphone

- Client capture (`MicCapturer`, 48 kHz mono int16): WASAPI `eCapture` default
  endpoint on Windows; an AudioQueue input on macOS.
- Wire: the existing audio datagram (`KindAudio`) carries a flow (byte 1:
  desktop 0, mic 1), a codec (byte 2: Opus 0, PCM16 1) and the frame length
  (byte 3, quarter milliseconds; 0 means 10 ms). Older peers wrote zeros
  there, which reads as desktop Opus 10 ms.
- Codec: Opus VoIP mono 10 ms; raw PCM16 mono 5 ms (480 B) on a LAN path.
- Host: one jitter buffer and play-out loop per session, reusing
  `JitterBuffer` and `Playout` (Opus PLC; PCM conceals by fading the last frame).
- Host sink (`MicSink`): writes into a user-installed virtual device found by
  name — Windows render endpoints "Steam Streaming Microphone" or "CABLE Input",
  macOS output devices "BlackHole", or a user-given substring. Nothing is
  bundled. No device: the host reports a hint instead.
- Echo: the client mic starts muted every session; Ctrl+Alt+U or the
  overlay's Sound & mic tray toggles it.

## Clipboard

- `pkg/clipboard.Board`: `Watch`, `Read`, `Write`. Windows uses a message-only
  window with `AddClipboardFormatListener`; macOS polls
  `NSPasteboard.changeCount` every 200 ms; Linux is a stub.
- Formats: UTF-8 text and PNG. Windows reads `PNG` or `CF_DIBV5`/`CF_DIB` and
  writes `PNG` + `CF_DIB`; macOS reads `public.png` or TIFF (converted by
  `NSBitmapImageRep`).
- Skipped content: Windows `ExcludeClipboardContentFromMonitorProcessing`,
  `CanIncludeInClipboardHistory`=0; macOS `org.nspasteboard.ConcealedType`,
  `TransientType`, `AutoGeneratedType`.
- Transport: each sender opens one QUIC unidirectional stream (type byte 0x01)
  and writes framed items (format, origin ID, SHA-256, length, bytes). Video
  and input never wait on it. Items over 16 MiB are refused by the sender and
  drained by the receiver.
- Loops: `clipboard.Guard` drops items from our own origin, and local changes
  whose hash equals the last applied remote item. Contents are never logged.
- Toggles: host `-clipboard` policy (host→client, client→host) and client
  settings (send, receive). Each side tells the other with `PeerState`, so a
  sender skips items the peer would drop.

## Negotiation

New Hello bits: `FeaturePeerState` (reads `MsgPeerState`), `FeatureMic` (host
accepts the mic flow), `FeatureClipboard` (handles clipboard streams). A peer
sends `PeerState` only to a peer with `FeaturePeerState`, so older peers never
see an unknown message.
